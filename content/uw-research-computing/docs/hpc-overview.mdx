# High-Performance Computing at CHTC

The CHTC High Performance Computing (HPC) cluster provides dedicated support for large, 
singular computations that use specialized software (i.e. MPI) to achieve internal 
parallelization of work across multiple servers using dozens to hundreds of cores. 

**Is high-performance computing right for me?**

High Performance Computing systems specialize in running a few, very large jobs that use multiple computers working together on the same problem. On the other hand, High Throughput Computing systems specialize in running tens to millions of small, independent jobs.

# HPC Hardware and Configuration

The HPC Cluster consists of one login node and many compute (aka execute) 
nodes. All users log in at the login node, and all user files on the shared file sytem are accessible on all nodes.
Additionally, all nodes are tightly networked (200 Gbit/s Infiniband) so
they can work together as a single \"supercomputer\", depending on the
number of CPUs you specify.

## Execute Nodes and Partitions

Only execute nodes will be used for performing your computational work. 
The execute nodes are organized into several partitions:

  | Partition | p-name | \# nodes (N) | t-default | t-max | max cores/job | cores/node (n) | RAM/node (GB) |
  | --- | --- | --- | --- | --- | --- | --- | --- |
  | Shared | `shared` | 45 | 1 day | 7 day | 320 | 64 or 128 | 512
  | Interactive | `int` | 2 | 1 hr | 4 hrs | 16 | 64 or 128 | 512 (max 64 per job)
  | Pre-emptable (backfill) | `pre` | 45 | 4 hrs | 24 hrs | 320 | 64 or 128 | 512
  | Owners | *unique* | 19 | 24 hrs | 7 days | *unique* | 64 or 128 | 512

* Researchers in a research group with their own hardware may access to additional partitions prioritized for their group.
* The `shared`, `pre`, and `int` partitions are **available to all HPC users**.
  - `shared` is the default partition.
  - `int` consists of two compute nodes intended for short and immediate interactive testing on a single node.
  - `pre` encompasses all nodes and is intended for more immediate turn-around of shorter, smaller, and/or 
interactive sessions requiring more than the 4 hour time limit of the `int` partition.
Jobs submitted to `pre` are run as backfill on any idle nodes, including researcher-owned 
compute nodes, meaning these jobs may be pre-empted by higher priority 
jobs. By default, pre-empted jobs will be re-queued (to run again) if they were submitted with 
an sbatch script.


## Fair Share Allocation

### Job limit / CPU limit

To promote fair access to HPC computing resources, across the `shared`, `pre`, and `int` partitions, all users are limited to:
* 10 concurrently running jobs
* A total of 720 cores across all running jobs

*These limits do not apply in researcher-owned partition.*

### Job priority

When determining which order to run jobs, the following policies are applies, in order or significance
to job priority determinations:

1. **User priority decreases as the user accumulates hours of CPU time over the last 21 days, across 
all queues.** This "fair-share" policy means that users who have run many/larger jobs in the near-past 
will have a lower priority, and users with little recent activity will see their waiting jobs start sooner. 
(The cluster does not have a strict "first-in-first-out" queue policy.)

1. **Job priority increases with job wait time.** After the history-based user priority calculation in (1), 
the next most important factor for each job's priority is the amount of time that each job has already 
waited in the queue. For all the jobs of a single user, these jobs will most closely follow a "first-in-first-out" policy.

1. **Job priority increases with job size, in cores.** This least important factor slightly favors larger jobs, so that 
the scheduler can take advantage when large numbers of newly-available nodes happen to become available (requiring less 
wasted time to deliberately drain nodes for larger jobs). So, among a user's jobs submitted at roughly the same time, 
a larger job may run first, if the number of nodes necessary for the larger job is already available.


# Data Storage and Management

## Data spaces

You will have access to two data spaces, `/home` and `/scratch`, each intended for different purposes. These data spaces are on a shared filesystem, accessible to the Access Point and all execute nodes.

| | `/home` | `/scratch` |
| --- | --- | --- |
| Purpose | Repeatedly used files, i.e., submit file templates, source code, software installations, databases | Submit files, working data, individual job inputs/outputs, logs, stderr/stdout files |
| Default quota (disk) | 30 GB | 100 GB |
| Default quota (number of items) | 250,000 | 250,000 | 

<Tip header="What about `/software`?">
We are deprecating `/software`. Users should install software in `/home`.
</Tip>

**CHTC staff reserve the right to remove any significant amounts of data
on the HPC Cluster** in our efforts to maintain filesystem performance
for all users.

<Tip header="⛔ No long-term storage">
**CHTC does not back up any data.** Treat the data space as temporary.

Only files necessary for *actively-running* jobs should be kept on the filesystem, and files should be removed from the cluster when jobs complete. A primary copy of any essential files (e.g. software, submit files, input) should be kept in an 
alternate, non-CHTC storage location.
</Tip>

## Manage data

### See your quota
Use the command `get_quotas` to see your disk and items quota.

<Terminal>
```
[username@spark-login ~]$ get_quotas
Path               Disk_Used(GB)  Disk_Limit(GB)  Files_Used  File_Limit
/home/username     18.6423        30              357650      500000
/scratch/username  2.37131        100             252         250001
```
</Terminal>

### See quota for a certain directory
Use the command `get_quotas -p <path>` to see the quota for a certain path, such as a group directory.
<Terminal>
```
[username@spark-login ~]$ get_quotas -p /home/groups/my_group
Path                    Disk_Used(GB)  Disk_Limit(GB)  Files_Used  File_Limit
/home/groups/my_group/  7.48749        30              117426      500000
```
</Terminal>

### Use `ndcu`

Alternatively, the `ncdu` command can also be used to see how many 
files and directories are contained in a given path:


<Terminal>

``` 
[username@hpclogin1 ~]$ ncdu /home/username
[username@hpclogin1 ~]$ ncdu /scratch/username
```

</Terminal>


When `ncdu` has finished running, the output will give you a total file
count and allow you to navigate between subdirectories for even more
details. Type `q` when you\'re ready to exit the output viewer.
